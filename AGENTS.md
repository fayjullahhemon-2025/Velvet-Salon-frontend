# AGENTS.md — SalonBook (Client Repository)

## 1. Project Context & Architecture Overview
**SalonBook** is a full-stack salon appointment booking platform where customers browse salon services, inspect service details, submit appointment requests, and pay for confirmed appointments via Stripe, while administrators manage services, appointments, users, and payment transactions[cite: 2, 3].

* **Client Stack**: Next.js (App Router), TypeScript/JavaScript, Tailwind CSS / semantic CSS variables, Better Auth client, Stripe Checkout, ImgBB image uploads[cite: 2, 3, 4, 23].

* **Data & Auth Model**:
  * Better Auth manages authentication sessions/accounts; application users carry `role` (`"customer"` | `"admin"`) and `isBlocked` (`boolean`)[cite: 10, 11, 15, 21].
  * Primary domain collections in MongoDB: `users`, `services`, `appointments`, and `transactions`[cite: 21].
* **Submission & Git Rules**:
  * Maintain separate client and server repositories with clear `README.md` files (never commit `.env` or secret values)[cite: 4].
  * Aim for at least 20 meaningful client-side commits with descriptive commit messages[cite: 4].

## 2. UI, Design System & Color Palette Guardrails
Follow the semantic design tokens strictly so contrast and visual hierarchy remain consistent across desktop, tablet, and mobile[cite: 19, 20, 23].

### Raw Foundation Tokens
* `color.text.primary` = `#666666`[cite: 23]
* `color.text.secondary` = `#333333`[cite: 23]
* `color.text.tertiary` = `#ffffff`[cite: 23]
* `color.text.inverse` = `#212529`[cite: 23]
* `color.surface.base` = `#000000`[cite: 23]
* `color.surface.muted` = `#d9842f`[cite: 23]
* `color.surface.strong` = `#f1e7df`[cite: 23]

### Semantic Color Tokens (Use These in Components/Stylesheets)
| Semantic Token | Resolved Hex | Role & Contrast Guardrail |
| :--- | :--- | :--- |
| `--bg-canvas` | `#f1e7df` | Primary light storefront/page background[cite: 23]. |
| `--bg-surface-card` | `#ffffff` | Service/appointment cards and elevated panels[cite: 23]. |
| `--bg-surface-dark` | `#000000` | Hero banners, dark headers, and footer blocks[cite: 23]. |
| `--bg-accent-brand` | `#d9842f` | Primary CTA buttons, active status badges, highlights[cite: 23]. |
| `--fg-primary` | `#333333` | Primary body text on `--bg-canvas` (`10.7:1`) and `--bg-surface-card` (`12.6:1`)[cite: 23]. |
| `--fg-muted` | `#666666` | Secondary metadata on `--bg-surface-card` (`5.74:1`). Do **not** use on `--bg-canvas` for body copy under `16px`[cite: 23]. |
| `--fg-inverse` | `#ffffff` | Primary text on `--bg-surface-dark` (`21:1`)[cite: 23]. |
| `--fg-on-accent` | `#212529` | Text on `--bg-accent-brand` (`6.3:1`)[cite: 23]. |
| `--border-subtle` | `rgba(102, 102, 102, 0.2)` | Dividers and default input borders[cite: 23]. |
| `--border-focus` | `#d9842f` | Keyboard `:focus-visible` indicator[cite: 23]. |

### Strict UI Rules
* **Never** use raw hex values inside component styles; always reference `--bg-*`, `--fg-*`, and `--border-*` tokens[cite: 23].
* **Never** pair `--fg-inverse` (`#ffffff`) on `--bg-accent-brand` (`#d9842f`) (`2.9:1` contrast fails WCAG AA). Always use `--fg-on-accent` (`#212529`) on `--bg-accent-brand`[cite: 23].
* **No browser `alert()`**: Use toast notifications for success and error feedback[cite: 19].
* **Loading & Error States**: Display meaningful loading states during service fetches, dashboard loads, booking submissions, and payment flows; handle invalid IDs, unauthorized access, booking conflicts, upload failures, and cancelled/failed payments gracefully[cite: 10, 17, 19].

## 3. Routes, Navigation & Role-Based Features

### Global Layout
* **Navbar**:
  * Brand: `SalonBook`[cite: 6].
  * Public routes: `Home`, `Browse Services`, `Sign In`, `Sign Up`[cite: 6].
  * Authenticated routes: `Home`, `Salon Details Page`, `Dashboard` (role-matched), plus Profile Dropdown (`User Name`, `Dashboard`, `Logout`)[cite: 6].
  * Must reflect auth changes immediately without requiring a full manual reload[cite: 6].
* **Footer**: Logo + short description, important navigation links, salon contact info, salon address & opening hours, social media links, and copyright[cite: 7].

### Public Pages
1. **Home (`/`)**:
   * **Banner**: Title, short description, `Explore Salon Services` CTA button, and salon-themed background[cite: 8].
   * **Featured Salon Services**: At least 6 `active` services from DB showing image, name, category, price, duration, short description, and `View Details`[cite: 8].
   * **Salon Service Categories**: Category cards/filters (e.g., Haircut & Styling, Hair Coloring, Hair Treatment, Facial & Skincare, Makeup, Manicure & Pedicure, Spa & Massage) enabling category exploration[cite: 8, 9].
   * **Extra Section**: 1 additional section (e.g., How Booking Works / Client Highlights)[cite: 9].
2. **Browse Services (`/services` or `/browse-services`)**:
   * Public responsive grid of `active` services[cite: 9, 20].
   * Supports **search by service name**, **filter by category**, and **sort by price**[cite: 9, 20].
3. **Sign Up (`/sign-up`) & Sign In (`/sign-in`)**:
   * Better Auth email/password + Google OAuth[cite: 10, 11].
   * Sign Up fields: `Full Name`, `Email`, `Password` (min 6 chars, 1 uppercase, 1 lowercase), and `Profile Image` (upload or URL)[cite: 10].
   * Never expose admin creation in public signup; redirect after auth based on role and block `isBlocked` users[cite: 10, 11, 15].

### Protected Routes & Role Dashboards
* **Salon Details (`/services/[id]`)**:
  * Protected route (redirect unauthenticated users to Sign In; handle invalid service IDs cleanly)[cite: 7, 10].
  * Shows service name, image, category, description, price, estimated duration, and booking form[cite: 10].
  * Booking form fields: `Appointment Date`, `Available Time Slot` (predefined list), and optional `Additional Message`[cite: 17].
  * Only authenticated `customer` users can book `active` services; `admin` users cannot submit customer bookings[cite: 10, 17].
* **Customer Dashboard** (Sidebar + Main Content Area; customers only):
  * **Overview**: Total Appointment Requests, Pending, Confirmed, Cancelled counts[cite: 12].
  * **My Appointments**: Lists customer's own appointments (service name & image, category, appointment date, time slot, service price, appointment status, payment status, request date), details view, **cancel pending only**, and **Pay Now** on **confirmed + unpaid** appointments[cite: 12, 13, 17].
  * **My Profile**: Update `name`, `image` (upload/URL), and basic fields like `phone` (cannot self-modify `role` or `isBlocked`)[cite: 11, 18].
* **Payment Result Pages**:
  * Stripe Success page (shows confirmation & verified status) and Stripe Cancel page[cite: 17, 18].
* **Admin Dashboard** (Sidebar + Main Content Area; admins only):
  * **Overview**: Total Registered Customers, Total Active Services, Total Appointment Requests, Pending Appointments, Confirmed Appointments, Total Successful Payments[cite: 13].
  * **Manage Services / Add & Update Service**: View all services, create/update/delete services, toggle `active` / `inactive`, upload service image via ImgBB (no raw image URL input in the service form), enforce positive `price` and `duration`[cite: 14].
  * **Manage Appointments**: View all bookings with customer info, service info, date/time, optional message, price, statuses, and request date; confirm `pending` appointments; cancel `pending` or `confirmed` appointments[cite: 14, 15, 17].
  * **Manage Users**: View registered customers, inspect user details, and block/unblock users[cite: 15].
  * **Transactions**: View transactions (customer info, related service, appointment date, amount, currency, Stripe session ID/short ref, status, transaction date); read-only (no manual override of unsuccessful payments to successful)[cite: 15, 16, 21].
  * **My Profile**: Update admin profile details[cite: 7, 18].

## 4. Backend Integration & Development Workflow (`../velvet-chair-backend/*`)

### Working With the Backend Codebase
* Inspect `../velvet-chair-backend/*` before adding or changing frontend API calls so request payloads, response shapes, cookie/session behavior, and route paths stay aligned.
* Never rely solely on frontend route hiding—the backend enforces authentication, `isBlocked`, ownership, and role permissions on every protected endpoint[cite: 4, 11, 12, 18].
* Payment completion is authoritative only after a verified Stripe webhook updates the appointment and `transactions` collection on the backend[cite: 4, 17, 18].

### Recommended Step-by-Step Build & Verification Order
1. **Design System & Layout Shell**: Configure semantic CSS variables from `color_palette_tokens.md`, `Navbar`, `Footer`, toast system, and loading/error components[cite: 6, 7, 19, 23].
2. **Auth & Route Guards**: Wire Better Auth client flows (`Sign In`, `Sign Up`, Google login, logout) and enforce customer vs. admin route guards across refreshes and direct URL navigation[cite: 5, 7, 10, 11].
3. **Public Service Discovery**: Build `Home` and `Browse Services` with search by name, category filtering, and price sorting against `GET /api/services`[cite: 8, 9, 20].
4. **Service Details & Booking Flow**: Build `/services/[id]`, handle invalid/inactive services, and wire the booking form to `POST /api/appointments` with conflict/validation error handling[cite: 10, 17, 19].
5. **Customer Dashboard**: Build Overview stats, My Appointments (cancel pending, trigger Stripe Checkout session for confirmed + unpaid), Success/Cancel pages, and My Profile[cite: 12, 13, 17, 18].
6. **Admin Dashboard**: Build Overview stats, Service management with ImgBB uploads, Appointment confirmation/cancellation, User block/unblock, Transactions list, and Admin Profile[cite: 13, 14, 15, 16, 18].
7. **End-to-End & Deployment Check**: Test reload safety on all routes, private route refresh, role isolation, ImgBB uploads, Stripe test payments + webhook status updates, and confirm zero `.env` files are staged[cite: 4, 5, 22].
