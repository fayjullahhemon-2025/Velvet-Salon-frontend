# AGENTS.md — VelvetSaloon Frontend

Salon booking client (browse services, book appointments, pay via Stripe; admins manage services/appointments/users/transactions). **Current state: scaffolding only** — create-next-app + Better Auth + MongoDB are wired; almost none of the product features below exist yet. Backend is the sibling repo `../velvet-saloon-backend`.

## Commands

- `npm run dev` — Next dev server (Turbopack).
- `npm run build` / `npm run start`.
- `npm run lint` — `biome check` (lint **and** format). Currently fails with pre-existing errors — that's not your regression.
- `npm run format` — `biome format --write`. There is no lint autofix script; run this for formatter errors.
- Typecheck: no script. Use `npx tsc --noEmit` (passes on clean tree).
- No test runner, no CI, no pre-commit hooks. Verification order: `format` → `lint` → `npx tsc --noEmit` → `npm run build`.

## Auth & environment (Better Auth + MongoDB)

- Server config: `src/lib/auth.ts` — MongoDB adapter, **DB name hardcoded** to `Velvet-Saloon-DB`, email/password enabled, social provider is **GitHub** (not Google).
- Route handler: `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`).
- Client: `src/lib/auth-client.ts` exports `authClient`, `signIn`, `signUp`, `useSession`, `signOut`; `baseURL` read from `BETTER_AUTH_URL`.
- `.env` keys present: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `MONGODB_URL`, `IMGBB_API_KEY`. Code also reads `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET`, which are **missing** from `.env` — social login will fail until added.
- Users carry `role: "customer" | "admin"` and `isBlocked`. The backend must enforce this on every protected endpoint; frontend route hiding is not enough.

## Backend (`../velvet-saloon-backend`)

- Bare Express + native MongoDB (no Mongoose) skeleton: `index.js`, port `5000`, only a health-check route. No Better Auth, Stripe, or domain routes yet.
- Before adding/changing frontend API calls, inspect it so payloads, response shapes, cookies, and route paths stay aligned. Payment is authoritative only after a verified Stripe webhook updates `appointments`/`transactions` there.

## Product requirements (planned — not implemented)

Build order the project expects: design tokens & layout shell → auth & route guards → public service discovery → service details & booking → customer dashboard → admin dashboard → end-to-end checks.

- Routes: `/`, `/services` (browse: search by name, filter category, sort price), `/services/[id]` (protected booking form: date, time slot, optional message), `/sign-in`, `/sign-up`, customer dashboard (overview, my appointments, profile), admin dashboard (overview, manage services/appointments/users, transactions, profile), Stripe success/cancel pages.
- Roles: only authenticated `customer` may book `active` services; admins cannot book. Customers cancel **pending** only; **Pay Now** only on confirmed + unpaid. Transactions are read-only. Block `isBlocked` users after auth.
- Sign-up: full name, email, password (min 6, 1 upper, 1 lower), profile image (upload or URL). Never expose admin creation publicly.
- Admin service forms: ImgBB image upload (no raw URL field), positive `price`/`duration`, active/inactive toggle.
- Design: use semantic tokens `--bg-*` / `--fg-*` / `--border-*` (source doc `color_palette_tokens.md` is **not in this repo** — find it before implementing; current `globals.css` is still stock shadcn). Never hardcode hex in components. Never put white on the `#d9842f` accent (fails WCAG AA) — use `#212529`.
- No browser `alert()` — use toasts. Loading/error states on all async flows (fetches, booking, payment, uploads).
